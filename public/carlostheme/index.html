ROCmFP4 Field Notes

How my AMD inference workbench came together.

My most meaningful development moment was not a single benchmark. It was the stretch where my ROCmFP4 and ROCmFPX work started looking like a usable AMD inference path: explicit GGUF formats, AMD build instructions, backend decode coverage, speculative model support, and repo notes other people could audit.

The inflection

From format work to an AMD workbench.

The useful shift in my recent work is that the pieces started serving one operating goal: make low-bit AMD inference buildable, explainable, and testable in the open. The claim here is limited to my public repos and commit history.

1. I kept the format explicit.

ROCmFPX and ROCmFP4 are treated as model-weight format work in GGUF, with block structure, scale handling, and CPU, HIP/ROCm, and Vulkan implementation paths described in the repos instead of being hidden behind one speed claim.

2. I made AMD builds a first-class path.

The `rocmfp4-llama` docs and scripts call out AMD architecture choices and ROCm/Vulkan build routes so RDNA and Strix-class users can reproduce the fork instead of rediscovering the flags.

3. I kept widening model coverage.

My commits move through Qwen, Gemma, Step, Diffusion Gemma, and related MTP/speculative paths. That matters because a format fork becomes useful when it survives more than one model family.

What changed technically

The work became easier to build, test, and extend.

Format discipline

I kept ROCmFPX and ROCmFP4 tied to explicit GGUF block and scale behavior plus backend implementation notes. That makes a low-bit format easier to reason about than a loose speed claim.

AMD build discipline

I added and maintained architecture-aware build paths and docs so the repo can be used on AMD systems without rediscovering the same flags.

Speculative model support

EAGLE3 and Step MTP3 support show the speculative layer being adapted to different state and head layouts instead of being locked to one path.

Decode coverage

Vulkan CM2/vector decode and related backend work keep the compressed formats connected to real execution paths.
